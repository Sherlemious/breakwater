# Mitigation Layer

The mitigation service is Phase C of the pipeline. It is a SQLite-backed simulation of firewall mitigation. It does not execute shell commands. Instead, it reads model events from a JSON file, decides the mitigation action, stores the generated `iptables` command in SQLite, and updates future traffic-window data when an IP is blocked.

## Input

Default input file:

```text
/app/data/mitigation_events.json
```

Default Docker command:

```bash
python -m mitigation --events-file /app/data/mitigation_events.json
```

Local command:

```bash
PYTHONPATH=. python3 -m mitigation --events-file path/to/events.json --db data/test.db
```

The event file may contain either one JSON object:

```json
{
  "id": 123,
  "flag": true,
  "level": 72,
  "type": "Volumetric_attacks"
}
```

or an array of JSON objects:

```json
[
  {
    "id": 123,
    "flag": true,
    "level": 72,
    "type": "Volumetric_attacks"
  },
  {
    "id": 124,
    "flag": false,
    "level": 10,
    "type": "Application-layer"
  }
]
```

## Required Keys

| Key | Type | Meaning |
|---|---:|---|
| `id` | integer | The `traffic_windows.window_id` generated by ingestion. |
| `flag` | boolean | Whether mitigation should process this event. If `false`, nothing is written. |
| `level` | integer | Severity from `0` to `100`. |
| `type` | string | Attack category from the model layer. |

Allowed `type` values:

```text
Volumetric_attacks
Network_protocols
Application-layer
```

The mitigation layer maps these to SQLite alert types:

| Model type | SQLite `active_alerts.alert_type` |
|---|---|
| `Volumetric_attacks` | `volumetric` |
| `Network_protocols` | `protocol` |
| `Application-layer` | `application` |

Invalid events fail fast with an error. Examples of invalid input:

```text
missing id
id is not an integer
flag is not boolean
level is outside 0-100
type is not one of the allowed values
```

## SQLite Tables Used

The service uses the existing schema. No migration is required.

Reads:

```text
traffic_windows
ip_list
```

Writes:

```text
active_alerts
active_mitigations
traffic_windows
window_anomaly_scores
```

`traffic_windows` and `window_anomaly_scores` are only changed when a `block_ip` action is chosen.

## Context Resolution

For each event, mitigation treats:

```text
event.id = traffic_windows.window_id
```

It loads the matching traffic window:

```sql
SELECT *
FROM traffic_windows
WHERE window_id = ?;
```

The mitigation context is derived from that row:

| Field | Use |
|---|---|
| `top_src_ip` | Main mitigation target. |
| `top_dst_port` | Service/port target for protocol-specific blocking. |
| `proto_tcp_frac` | Helps infer protocol. |
| `proto_udp_frac` | Helps infer protocol. |
| `proto_icmp_frac` | Helps infer protocol. |
| `proto_other_frac` | Helps infer protocol. |
| `syn_ratio` | If `>= 0.5`, protocol is treated as TCP. |
| `pkt_s` | Stored as a triggered feature. |
| `bytes_s` | Stored as a triggered feature. |

If `top_src_ip` is missing, the service writes an alert only and does not create a mitigation rule.

## Whitelist and Blacklist

The service checks `ip_list` before choosing an action.

Whitelist lookup:

```sql
SELECT 1
FROM ip_list
WHERE ip = ? AND list_type = 'whitelist';
```

Blacklist lookup:

```sql
SELECT 1
FROM ip_list
WHERE ip = ? AND list_type = 'blacklist';
```

Behavior:

| Case | Result |
|---|---|
| IP is whitelisted | Alert only. No mitigation rule. |
| IP is blacklisted | Immediate `block_ip`, even if severity is low. |

Whitelist has priority over blacklist if an IP appears in both lists.

## Decision Policy

If `flag=false`, the event is ignored and nothing is written.

For `flag=true`, the decision is:

| Level | Action |
|---:|---|
| `0-30` | Alert only. |
| `31-60` | Lenient `rate_limit`. |
| `61-80` | Strict `rate_limit`. |
| `61-80` and `type=Network_protocols` with known TCP/UDP port | `block_port`. |
| `81-100` | Temporary `block_ip`. |

Rule durations:

| Rule type | Expiry |
|---|---:|
| lenient `rate_limit` | 15 minutes |
| strict `rate_limit` | 30 minutes |
| `block_port` | 30 minutes |
| `block_ip` | 60 minutes |

## Generated Commands

Commands are stored in SQLite only. They are not executed.

`block_ip`:

```bash
iptables -A INPUT -s <ip> -j DROP
```

Example:

```bash
iptables -A INPUT -s 192.168.1.20 -j DROP
```

`block_port`:

```bash
iptables -A INPUT -s <ip> -p <proto> --dport <port> -j DROP
```

Example:

```bash
iptables -A INPUT -s 192.168.1.20 -p tcp --dport 80 -j DROP
```

`rate_limit`:

```bash
iptables -A INPUT -s <ip> -m hashlimit --hashlimit-above <rate>/second --hashlimit-burst <burst> --hashlimit-mode srcip --hashlimit-name <name> -j DROP
```

Lenient rate limit:

```text
rate = 100/second
burst = 200
```

Strict rate limit:

```text
rate = 25/second
burst = 50
```

Example:

```bash
iptables -A INPUT -s 192.168.1.20 -m hashlimit --hashlimit-above 25/second --hashlimit-burst 50 --hashlimit-mode srcip --hashlimit-name limit_192_168_1_20 -j DROP
```

## SQLite Output

### `active_alerts`

For each valid `flag=true` event, the service inserts one alert.

Important fields:

| Column | Value |
|---|---|
| `alert_type` | `volumetric`, `protocol`, or `application`. |
| `severity` | `low`, `medium`, `high`, or `critical`. |
| `anomaly_score` | `level / 100.0`. |
| `window_id_start` | Input `id`. |
| `window_id_end` | Input `id`. |
| `source_ips` | JSON array containing `top_src_ip`. |
| `triggered_features` | Comma-separated feature names. |
| `description` | Human-readable decision reason. |
| `created_at` | Unix timestamp. |

Severity mapping:

| Level | Severity |
|---:|---|
| `0-30` | `low` |
| `31-60` | `medium` |
| `61-80` | `high` |
| `81-100` | `critical` |

Example alert row:

```text
alert_type: volumetric
severity: high
anomaly_score: 0.72
window_id_start: 123
window_id_end: 123
source_ips: ["192.168.1.20"]
triggered_features: pkt_s,bytes_s,top_src_ip,top_dst_port,syn_ratio
description: strict; level=72; type=Volumetric_attacks
```

### `active_mitigations`

If the selected action is not alert-only, the service inserts or updates one mitigation.

Important fields:

| Column | Value |
|---|---|
| `rule_type` | `rate_limit`, `block_port`, or `block_ip`. |
| `target` | IP address, or `ip:protocol/port` for port blocks. |
| `iptables_cmd` | Generated command string. |
| `alert_id` | The alert created for this event. |
| `applied_at` | Unix timestamp. |
| `expires_at` | Unix timestamp when the simulated rule expires. |
| `revoked_at` | `NULL` while active. |
| `notes` | Includes `simulated; command stored but not executed`. |

Example mitigation row:

```text
rule_type: block_ip
target: 192.168.1.20
iptables_cmd: iptables -A INPUT -s 192.168.1.20 -j DROP
notes: simulated; command stored but not executed; level=90; type=Volumetric_attacks; critical block; level=90; type=Volumetric_attacks
```

## Duplicate Prevention

Before inserting a mitigation, the service checks for an active rule with the same `rule_type` and `target`:

```sql
SELECT mitigation_id, expires_at, notes
FROM active_mitigations
WHERE rule_type = ?
  AND target = ?
  AND revoked_at IS NULL;
```

If one exists:

```text
no duplicate row is inserted
expires_at is extended if the new expiry is later
notes are updated
```

## Traffic Window Effect

For a `block_ip` action, the service simulates the firewall effect by removing future traffic windows from the same PCAP run.

It deletes future rows where:

```text
traffic_windows.run_id = triggering window run_id
traffic_windows.ts > triggering window ts
traffic_windows.top_src_ip = blocked IP
```

Before deleting those rows, it also:

```text
deletes related rows from window_anomaly_scores
resolves active alerts that reference those future windows
nulls their window references so SQLite foreign keys remain valid
```

This means that after IP `x` is blocked at time `t`, the dashboard should not show later traffic windows where `x` is the `top_src_ip`.

Limitation: `traffic_windows` is aggregated per time window. The current schema does not store every packet or every source IP inside a mixed window. Therefore, mitigation can remove future windows where the blocked IP is the top source, but it cannot remove only that IP's packets from a window where another IP is the top source.

## CLI Output

The CLI prints a JSON array of processing results.

Example:

```json
[
  {
    "alert_id": 7,
    "command": "iptables -A INPUT -s 192.168.1.20 -j DROP",
    "mitigation_id": 3,
    "reason": "critical block; level=90; type=Volumetric_attacks",
    "removed_windows": 4,
    "rule_type": "block_ip",
    "status": "mitigated",
    "target": "192.168.1.20",
    "window_id": 123
  }
]
```

Possible statuses:

| Status | Meaning |
|---|---|
| `ignored` | `flag=false`; no database writes. |
| `alert_only` | Alert was written, but no mitigation rule was created. |
| `mitigated` | Alert and mitigation were written. |
